# 美化：整理作者自己写的稿子

适用于用户自己写的稿子。作者的内容、观点、例子和口吻是这篇文章的价值所在：工作是让它更好读，而不是重写它。在主对话里直接做，不需要子代理。

输出 `<名>.polish.md`。下文的"素材"就是作者原稿。

## 1. 内容保全（红线）

- **句子默认原样保留**：原稿的句子只要通顺就一字不改，不要为了"更书面""更专业""更完整"去同义改写或扩写。
- 作者的口语化表达（如"卡住了再换""翻旧账"）和每条技巧开头的加粗短句是这篇文章的风格，必须原样保留。严禁把口语换成书面语或术语（如把"上下文越乱，答得越差"改成"容易引起逻辑干扰"）。
- 保持每条技巧的原有结构：原稿是"做法 + 理由/怎么做"的，改完仍然是，不能只留问题描述、丢掉建议。
- **不删内容**：每一条技巧、步骤、例子、正反对比（❌/✅）、注意事项、常见误区、模板、表格都要保留。只允许合并真正重复的表述、修正明显的错别字和病句。
- 逐字保留：代码块、提示词模板、命令、配置、文件名、产品名、数字、链接、引号里的示例话术。图片占位符 `![...](...)` 原样留在原来的上下文里。
- 保留作者的具体例子和口吻：作者举的行业、项目、工具例子不要替换成泛泛的说法；原有的第一人称可以保留，但不要新增。
- 保留说明性信息：资料来源、整理时间、适用范围、"以实际账号为准"这类说明要保留（可以放在开头导语或文末）。
- 不新增事实：不添加原稿没有的功能、数字、限定条件、结论或术语。"如""比如"后面的举例不能改写成上限或唯一选项；程度词和比较级与原稿一致。

## 2. 可以做的编辑（只限以下几类）

- **开头导语**：原稿开头已有说明或导语就沿用原句；没有时用 2~3 句话说清这篇讲什么、适合谁，只写原稿撑得住的话。
- **章节小标题**：`##` 小标题可以改得更具体、更有信息量，但不改变该节的内容范围；不带编号（排版时自动编号）。列表项开头的加粗短句不是小标题，不动。
- **结构**：章节顺序基本保持，只有明显不顺时才调整。过长的列表可以按主题分组成 `###` 小节；适合横向对比的内容可以整理成表格。
- **段落节奏**：过长的段落可以拆开，零碎的段落可以合并，拆合时句子本身不改。
- **衔接**：章节之间缺少过渡时补一句简短的过渡，不用设问，不添加原稿没有的判断。
- **收尾**：原稿结尾已经是实用内容（误区、模板、清单）就直接沿用；否则补一个小标题具体的 `##` 收尾章节，写读者能落地的信息，严禁金句、口号和感悟式升华。

## 3. 格式

- 不写一级标题，正文从导语或 `##` 开始，`###` 作子分类，不跳级。原稿一级标题若有信息量（系列名、期数），融入导语。
- 正文严禁 `---`、`***`、`___` 分割线。
- 原稿已有的加粗、行内代码、引用块、表格、列表格式基本沿用，不要为了"视觉丰富"额外堆加粗或 emoji。
- 语言底线：不用"这意味着/由此可见"层层推论；不用"你可能会问""话不多说"；不用空洞的"不是 X 而是 Y"；段末不加感悟式升华；不用破折号做解释。

## 4. 标题与摘要

按 titles.md 构思 5 个候选，和作者原标题一起比较后选定 `title`，再写 `digest`。

## 输出格式

```markdown
---
title: （选定的标题）
digest: （40~120 字）
（输入里有的 author / cover / thumb_media_id / theme / source_* 原样照抄）
---

（正文）
```

## 完成后

回复用户：输出文件路径、选中的标题和其余候选、做了哪几类编辑（如"拆了 3 个长段落、补了导语、2 个小标题改得更具体"）。提醒下一步可以排版。
